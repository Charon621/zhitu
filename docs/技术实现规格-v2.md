## 0. 这个系统到底要做什么

### 0.1 一句话

**给 AI 配一块不会被擦掉的黑板，黑板自己长成一张地图。**

### 0.2 用户是谁，他要什么

一个想快速入门或复习某个领域的人。他的三种典型状态：

1. **有明确目标**：想搞懂 AI 是怎么回事
2. **有具体问题**：想弄明白 softmax 为什么减最大值
3. **没有目标**：只是随便看看，不知道从哪开始

**关键约束：第三种状态是最常见的，也是最难做的。** 任何要求用户先声明"我要学什么"的设计都会在这一步流失用户。

### 0.3 用户的原话，逐条对应到设计

这些是需求的源头，任何实现决策都不能偏离它们：

| 用户原话 | 对应的设计 |
|---|---|
| 「通过和 AI 对话的方式从 0 开始发散」 | 对话是唯一入口，不预设课程结构 |
| 「当 AI 给出学习顺序和方向时，学习者从一个点开始」 | 首次只给 3 个入口，不给完整大纲 |
| 「自然而然地由 AI 引导至更深层次」 | 引导发生在对话内部，不跳转到别的页面 |
| 「我从一个小点发散到了非常远的距离，AI 该怎么把这条线包络进主线」 | 见 §5 归航机制 |
| 「形成类似于笔记的痕迹」 | 见 §4 实时笔记 |
| 「用户可以松弛有度，想纵横和拓深都可以」 | 见 §1.3 两种边 |
| 「日常聊天一律用连贯的正常段落」 | 见 §8.1 全局排版约束 |

### 0.4 三条不可动摇的设计原则

**第一，对话是原件，笔记是派生物。** 数据库里的 `turns` 表只追加、永不修改。所有笔记、地图、小结都是从 `turns` 推导出来的。抽取失败、模型换代、提示词重写，都可以重算，原始记录不动。这是整个系统能长期演进的前提。

**第二，发散是权利，不是错误。** 系统永远不会主动打断用户说"你跑偏了"。包络（把跑远的线收回来）必须在后台静默完成，只在用户主动回看时呈现。

**第三，界面要安静。** 不做打卡、不做徽章、不做排行榜、不做成就音效。这类设计带来的兴奋感三天就过去了，而学习是三个月的事。

## 1. 数据模型（完整，包含待建表）

### 1.1 已建成的表

数据库：SQLite（`better-sqlite3`），文件在 `app.getPath('userData')/zhitu.db`，WAL 模式，开启外键约束。表结构定义在 `src/main/core/db.ts`。

```
app_config(key, value, updated_at)                     -- 键值存储
topics(id, title, goal_kind, created_at, archived_at)  -- 一张大地图
sessions(id, topic_id, title, started_at, ended_at, summary_md)
turns(id, session_id, role, content, created_at)       -- 原件，只追加
concepts(id, canonical_name, aliases_json, note, created_at)
nodes(id, topic_id, concept_id, title, body_md, kind, status, mastery,
      origin_turn_id, created_at, updated_at, last_seen_at)
edges(id, src_id, dst_id, type, weight, created_at)    -- type: parent|prereq|related|answers
extractions(id, turn_id, node_id, status, payload_json, error, attempt, created_at, updated_at)
```

### 1.2 语义约定（容易搞错，逐条明确）

**`nodes.kind`** 四选一：`question`（一个待弄清楚的问题）、`concept`（一个需要理解的名词）、`fact`（一个可直接记住的结论）、`example`（一个具体案例、代码或资源）。

**`nodes.status`** 三选一：`open`（未收线，这条线还没走完）、`gathered`（已收线，结论已经明确）、`mastered`（已掌握）。默认 `gathered`。

**`nodes.mastery`** 整数 0 到 5：

```
0  只是提了一嘴，看过
1  有印象，说不清楚
2  理解了，能看懂别人怎么用
3  讲得出来，能给别人解释
4  用得出来，能自己动手做
5  能改进它，或指出它的局限
```

**`edges.type`** 四种，**前两种的区分是整个产品的核心，绝不能合并**：

| type | 含义 | 谁决定 | 用途 |
|---|---|---|---|
| `parent` | 我从哪个节点问到了这里 | 用户的实际思路轨迹 | 支持发散漫游，回答"我为什么学到这" |
| `prereq` | 要理解 A 客观上得先懂 B | 客观知识依赖，与用户思路无关 | 支持系统补基础、考前诊断 |
| `related` | 两个东西有关系，但不构成依赖 | 模型判断 | 弱连接，用于发现 |
| `answers` | A 回答了 B 这个问题 | 归航判定 | 收线时标记 |

> **实现警告**：如果只做 `parent`，产品就退化成漫游工具；如果只做 `prereq`，产品就退化成死板课程表。**两种必须同时存在，且 UI 上要用不同线型区分。**

### 1.3 待建的表

```sql
-- 附件：用户拖进来的文档、图片、PPT
CREATE TABLE attachments (
  id            TEXT PRIMARY KEY,
  session_id    TEXT REFERENCES sessions(id) ON DELETE CASCADE,
  turn_id       TEXT REFERENCES turns(id) ON DELETE SET NULL,  -- 哪一轮带进来的
  kind          TEXT NOT NULL,        -- pdf | image | docx | pptx | xlsx | md | txt | html | code
  original_name TEXT NOT NULL,
  stored_path   TEXT NOT NULL,        -- 原件存放位置，相对 userData
  bytes         INTEGER NOT NULL,

  extract_error TEXT,
  page_count    INTEGER,

);
CREATE INDEX idx_attachments_session ON attachments(session_id);
CREATE UNIQUE INDEX idx_attachments_hash ON attachments(sha256, session_id);

-- 附件切片：喂给模型的最小单位，也是笔记溯源的锚点
CREATE TABLE chunks (
  id            TEXT PRIMARY KEY,
  attachment_id TEXT NOT NULL REFERENCES attachments(id) ON DELETE CASCADE,
  ordinal       INTEGER NOT NULL,     -- 第几段/第几页
  text          TEXT NOT NULL,
  page          INTEGER,              -- 页码/幻灯片号，用于回指
  token_estimate INTEGER
);
CREATE INDEX idx_chunks_attachment ON chunks(attachment_id, ordinal);

-- 对话流水的扩展：附件、引用、笔记（不修改 turns，用扩展表）
CREATE TABLE turn_meta (
  turn_id       TEXT PRIMARY KEY REFERENCES turns(id) ON DELETE CASCADE,
  attachment_ids_json TEXT NOT NULL DEFAULT '[]',  -- 这一轮带了哪些附件
  cited_chunk_ids_json TEXT NOT NULL DEFAULT '[]', -- 模型回答时实际引用了哪些切片
  mode          TEXT NOT NULL DEFAULT 'guide'      -- guide | free | review
);

-- 笔记块：实时笔记的最小单元。一个 node 下可以挂多块
CREATE TABLE note_blocks (
  id            TEXT PRIMARY KEY,
  node_id       TEXT NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  block_type    TEXT NOT NULL,   -- claim | mece | example | contrast | pitfall | question | formula | source_quote | user_note
  content_md    TEXT NOT NULL,
  ordinal       INTEGER NOT NULL,
  origin_chunk_ids_json TEXT NOT NULL DEFAULT '[]', -- 溯源：来自哪个文档切片
  origin_turn_id TEXT REFERENCES turns(id) ON DELETE SET NULL,
  pinned        INTEGER NOT NULL DEFAULT 0,  -- 用户置顶，参与排序权重
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);
CREATE INDEX idx_note_blocks_node ON note_blocks(node_id, ordinal);

-- 学习者画像：不靠问卷，靠行为逐步积累
CREATE TABLE learner_profile (
  id            TEXT PRIMARY KEY DEFAULT 'singleton',
  level_estimate INTEGER NOT NULL DEFAULT 1,   -- 0..5，对应 mastery 同一套标尺
  confidence    REAL NOT NULL DEFAULT 0,       -- 0..1，样本越多越高
  signals_json  TEXT NOT NULL DEFAULT '{}',    -- 各项证据的计数
  updated_at    TEXT NOT NULL
);

-- 复习队列（间隔重复，第 6 阶段用）
CREATE TABLE reviews (
  node_id       TEXT PRIMARY KEY REFERENCES nodes(id) ON DELETE CASCADE,
  due_at        TEXT NOT NULL,
  interval_days REAL NOT NULL DEFAULT 1,
  ease          REAL NOT NULL DEFAULT 2.5,
  lapses        INTEGER NOT NULL DEFAULT 0,
  last_reviewed_at TEXT
);
CREATE INDEX idx_reviews_due ON reviews(due_at);

-- 全局搜索索引（FTS5，中文用 trigram 分词器）
CREATE VIRTUAL TABLE search_fts USING fts5(
  ref_kind,      -- node | note_block | turn | chunk

  text,
  tokenize = 'trigram'

```

### 1.4 迁移策略

`db.ts` 用 `PRAGMA user_version` 做版本控制，当前 `SCHEMA_VERSION = 1`。**每次加表或加列都要把版本号加一，并在 `migrate()` 里写一段幂等的升级 SQL。** 已发布过 0.1.0 和 0.1.1，用户机器上存在 v1 数据库，不能直接重建。

## 2. 运行时架构（已建成，只做说明）

### 2.1 进程与端口

```
Electron 主进程
 ├─ app.setName('zhitu')
 ├─ if (process.env.ZHITU_DATA_DIR) app.setPath('userData', ...)   ← 沙箱开关，测试用
 ├─ requestSingleInstanceLock()  ← 抢不到锁立刻 app.exit(0)
 ├─ openDatabase(userData/zhitu.db)
 ├─ Hono 服务监听 127.0.0.1:0（随机端口）
 │    └─ 每个请求校验 X-Zhitu-Token，token 每次启动随机生成
 ├─ BrowserWindow（contextIsolation: true, sandbox: false, nodeIntegration: false）
 └─ preload 通过 --zhitu-port= 和 --zhitu-token= 启动参数把端口和凭证交给渲染进程

渲染进程（React）
 └─ 只通过 HTTP 访问 127.0.0.1:<port>，没有任何 Node 能力
```

**关键约束**：渲染进程永远不能 require Node 模块，也永远不能直接访问数据库。所有数据出入口都是本地 HTTP 接口。这是为了将来能把后端换成独立进程（例如迁到 Tauri）时，改动限制在壳。

### 2.2 已有的接口

```
GET  /health
GET  /bootstrap                     → version, dataDir, settings, providers, levels, stats, latestSessionId
POST /settings                       → 保存设置（apiKey 单独处理）
POST /settings/test                  → 用临时参数或已存参数测试连通性
POST /chat                           → SSE 流式对话，事件：meta | delta | done | error
GET  /sessions
GET  /sessions/:id/turns
```

### 2.3 密钥处理（已建成）

`SettingsService` 用 Electron `safeStorage` 加密后写入 `app_config` 的 `secret.apiKey`，格式 `{v:1, encrypted:boolean, data:string}`。加密不可用时退回明文，但 `SettingsView.keyEncrypted` 会如实告诉界面，界面必须显示提示。

**任何时候都不能把明文密钥返回给渲染进程**，只能返回 `hasApiKey: boolean`。

### 2.4 错误处理约定（已建成）

`ProviderError` 携带 `message`（给用户看的原因）和 `advice`（给用户看的下一步建议），按 HTTP 状态码翻译：401 密钥无效、402 余额不足、404 地址或模型名错、429 太频繁、5xx 服务商故障、网络层错误单独一类。界面必须同时显示这两段文字。

## 3. 对话子系统（已有骨架，需增强）

### 3.0 第一次进入时发生什么（最容易做砸的地方）

用户装完软件，填完密钥，看到的第一个界面决定他会不会留下来。**最常见的死法是：一个空白输入框加一句"说点什么吧"，用户不知道该说什么，关掉，再也不打开。**

**目标流程**：

```
首次进入主界面
  └─ 不显示空白输入框，显示"开始卡片"
       ├─ 用户点「我想了解一下某个领域」
       │    └─ 输入领域名 → 选倾向 → 生成 3 个入口问题 → 点其中一个
       │         → 以该问题直接发起第一轮（用户不用再打字）
       ├─ 用户点下面列的问题示例
       │    → 以该问题直接发起第一轮
       ├─ 用户拖入文件
       │    → 建立附件 + 创建 resource 节点 → 以"这份资料讲了什么"发起第一轮
       └─ 用户自己打字
            → 正常对话
                    ↓
             对话开始，主题由第一句话自动生成
```

**开始卡片的样子**：

```
┌────────────────────────────────────────────┐
│  从哪儿开始都行                              │
│                                            │
│  这里是空的，聊起来就会长出东西。             │
│                                            │
│  想学点什么？                               │
│  ┌──────────────────────────────────────┐  │
│  │ 我想了解一下某个领域                   │  │ ← 点开输入领域名
│  └──────────────────────────────────────┘  │
│                          [ 开始 ]           │
│                                            │
│  或者，直接问一个问题：                      │
│   · 神经网络到底是怎么"学"的？              │
│   · 为什么 AI 能看懂一句话是什么意思？       │
│   · 大模型为什么会"胡说"？                  │
│                                            │
│  或者把资料拖进来（PDF / 图片 / PPT）         │
└────────────────────────────────────────────┘
```

**"我想了解一下某个领域"点开后的流程**（这是 §0.2 里第三种用户的主路径）：

用户输入领域名（比如"AI"），**不要立刻生成完整大纲**——那是教科书目录，会压垮零目标用户。改为：

1. 显示一个中间页，让用户选倾向（偏原理 / 偏动手 / 随便看看）。**这不是问卷，是给 AI 的指路牌**，页面上写明"这不锁定什么，随时可以改"。
2. 调用 `utilityModel` 生成 3 个具体入口问题，每个带一句"为什么建议从这个开始"。
3. 用户点其中任意一个，立刻以那个问题发起第一轮对话。**不要让用户再打一遍字。**
4. 主题（`topics` 行）在此时创建，标题就是领域名，`goal_kind` 记录倾向。

**生成入口的提示词**：

```
[system]
{{FORMAT_RULES}}

你在给一个刚接触某个领域的自学者挑三个起点。

要求：
每个起点必须是一个具体到能立刻开讲的问题，不能是一个话题名称。
反面例子是"线性代数"，正面例子是"为什么矩阵乘法要那样定义"。
三个起点里，第一个要最不容易劝退，最后一个可以稍微硬一点。
每条都要用一句大白话说明为什么建议从这个开始，不要超过 30 字。

只输出 JSON，不要解释：
{
  "entries": [
    { "question": "", "why": "" },
    { "question": "", "why": "" },
    { "question": "", "why": "" }
  ]
}

[user]
领域：{{domain}}
学习者倾向：{{principle | hands_on | casual}}
```

**重要的实现约束**：这个流程只在**该主题下还没有任何节点**时出现。一旦聊出东西了，再次打开主界面就是正常的对话界面加右侧栏。

### 3.1 现在是怎么工作的

`POST /chat` 收到消息后：先把用户这句话落进 `turns`（**先落库，再调模型**，这样后面出错也不丢），取最近 20 轮历史，拼上系统提示词，调服务商流式接口，逐段通过 SSE 推给界面，全部结束后把 AI 回答也落库。

### 3.2 必须替换的部分：工作集装配

**现状问题**：只带最近 20 轮，超出就丢。聊到第 50 轮时，AI 完全不记得"我们最开始是从注意力机制出发的"。

**目标**：把"最近 20 轮"换成 **工作集（Working Set）**，装配规则如下，总量控制在 6000 token 以内：

```
1. 本场主题与目标                     （必带，约 50 token）
2. 当前所在节点 + 它的祖先链（最多 5 层）  （必带，每节点约 60 token）
3. 当前节点的 prereq 前置（最多 3 个，只带标题）（约 60 token）
4. 兄弟节点标题列表（最多 5 个，只带标题）    （约 80 token）
5. 最近 8 轮完整对话                  （约 1500 token）
6. 向量/全文检索召回的、与当前问题相关的历史节点摘要（最多 5 个）（约 600 token）
7. 本场已产出的笔记块标题列表（最多 10 条，只带标题）（约 200 token）
8. 用户已导入的、与本问相关的文档切片（最多 3 段，每段 ≤ 500 字）（约 1200 token）
9. 系统提示词 + 学习者画像推断             （约 600 token）
```

**实现要点**：第 6 项在 v2 可以先用 FTS5（`search_fts`，trigram 分词器）实现，不要一上来做向量检索。第 9 项的学习者画像见 §9。

**验收**：聊到第 30 轮时问"我们最开始是从哪儿聊起来的"，AI 能准确说出起点。

### 3.3 三种模式

`turn_meta.mode` 三选一，通过请求体传入，界面顶部的切换按钮控制：

- **`guide`（引导）**：默认。AI 会主动给下一步建议、会提示前置知识。
- **`free`（自由）**：AI 只答不问，不做任何引导。
- **`review`（复习）**：AI 根据 `reviews` 队列和节点掌握度主动出题考用户，用户回答后 AI 判定掌握度。

三种模式**共用同一套提示词基底**，只在末尾追加一段模式说明。不要为每种模式写一整套新提示词。

## 4. 实时笔记子系统（本次重点，从零实现）

这一节的每一个约束都是为了解决同一个问题：**AI 生成的总结有极大概率变成没人看得进去的废话**。

### 4.1 废话是怎么产生的（必须先理解，否则实现必然跑偏）

**成因一：没有实指。** 如果提示模型"总结这段对话"，它会产出"本段讨论了 softmax 的作用及其数值稳定性问题"这类话——**这句话不包含任何信息，它只是给对话贴了一个标签**。任何人读了都学不到东西。

**成因二：重复原文。** 笔记如果只是把 AI 上一轮的话换个说法重写一遍，那用户为什么不直接看原文？笔记必须提供原文没有的东西。

**成因三：尺度失配。** 一次对话里可能只讲清了半个知识点。强行产出一篇"完整笔记"，就只能靠扩写和废话把篇幅撑起来。

**成因四：没有边界。** 用户问了一个追问，AI 又讲了一遍同样的东西，笔记里就会出现两条几乎一样的条目。

### 4.2 六条硬规则

**规则一：笔记只从 `assistant` 的回复里抽取，不从用户的话里抽取。**

用户的提问已经在 `turns` 里了，不需要复述。而且用户的原话往往粗糙，抽出来就是噪音。

**规则二：只抽"这一轮新增的认知"，不重复已有笔记。**

抽取时把该节点下已有的 `note_blocks.content_md` 一并送进提示词，明确要求"如果这一轮没有带来新的东西，返回 `hasNewContent: false`"。**宁可不记，也不要重复记。**

**规则三：每条笔记块必须能回答"读它比读原文省了什么"。**

四条具体判据，满足其一才允许产出：

```
1. 压缩：把 300 字讲清的东西压成一句话，且不丢关键条件
2. 结构化：把散在几段里的东西排成有顺序的几步
3. 对照：把两个容易混的东西并排放，指出区别在哪
4. 迁移：指出它和用户已经学过的另一个东西是同一回事
```

**规则四：每条笔记块的正文不许出现元话语。**

禁止出现："本段讨论了""文中提到""作者认为""综上所述""值得注意的是""总而言之"。这些词一旦出现，说明这条不是笔记，是摘要。

**规则五：没有把握的具体数字和断言，不许进笔记。**

模型如果在对话里说了"大约快 10 倍"这种话，抽取时必须判断：这是有依据的结论，还是随口一比？**随口一比的，进 `question` 类型或直接丢弃，绝不写进 `claim`。**

**规则六：允许多次追加，不追求一次成型。**

一次对话产出 1 到 3 条笔记块是正常量。**不要为了凑满一页而扩写。** 一张有三条实指内容的卡片，比一张有十条废话的卡片有用得多。

### 4.3 笔记块类型定义

每种类型都有明确的信息职责，抽取时按这个表判断：

| block_type | 职责 | 判定标准 | 反例（不要产出） |
|---|---|---|---|
| `claim` | 一个核心断言，用一句话说完 | 有主语、有结论、有条件 | 「讨论了数值稳定性」← 没有断言 |
| `mece` | 一组并列或递进的因素，穷尽且互斥 | 至少 2 项，项与项之间不重叠 | 「有好处也有坏处」← 太粗 |
| `example` | 一个能替代抽象解释的具体例子 | 可复现、可代入 | 「举个例子会更好理解」← 没举例 |
| `contrast` | 两个易混概念的区别 | 明确指出差异维度 | 「两者不同」← 没说哪里不同 |
| `pitfall` | 一个常见错误理解 | 错误本身要写清楚 | 「要注意细节」← 空话 |
| `question` | 这一步没解决、留着的问题 | 具体到可以继续追 | 「还需要深入学习」← 空话 |
| `formula` | 公式或伪代码 | 带变量说明 | 孤零零一个式子 |
| `source_quote` | 用户导入文档里的原文引用 | 必须带页码 | 无出处的转述 |
| `user_note` | 用户自己写的，AI 永不覆盖 | — | — |

### 4.4 触发时机

**不要在一轮对话中途抽取。** 触发点有两个：

**触发点一（主）**：`assistant` 的回复流式结束，且最终文本非空，且长度 ≥ 80 字。延迟 1.5 秒后启动抽取（等待用户可能的连续追问，避免为一次连续对话产生多条碎片）。

**触发点二（补）**：同一节点下累计超过 6 轮对话仍未抽取，强制抽取一次。

**并发控制**：每个 `session` 同一时刻只允许一个抽取任务在跑，用内存里的 Promise 队列串行化。抽取永远不阻塞对话，抽取失败不影响用户继续聊。

### 4.5 抽取调用规格

**模型选择**：抽取是高频、低难度的任务，用一个便宜快速的模型。设置里暴露两个模型配置：`model`（对话用）和 `utilityModel`（抽取、归航、出题用），`utilityModel` 未配置时回退到 `model`。

**输入构造**（发出去的完整内容）：

```
[system]
你是一个知识萃取器。你的任务不是总结，是把一次对话里真正有价值的东西
压缩成可以直接复习的最小单元。

判断标准：一条内容值得记下来，当且仅当它满足下面四条之一。
压缩：把一大段解释压成一句话，且不丢关键条件。
结构化：把散在几处的因素排成有顺序、穷尽、互斥的几项。
对照：把两个容易混淆的东西并排放，明确说出区别在哪。
迁移：指出它与另一个已有概念本质上是同一回事。

严格禁止：
不要产出元话语，例如"本段讨论了""文中提到""作者认为""综上所述"
"值得注意的是"。一旦出现这类词，说明你在做摘要而不是做笔记。
不要把对话里随口提到的、没有依据的具体数字写成断言。
不要重复已经存在于【已有笔记】里的内容。
不要为了凑篇幅而扩写。这一轮没有新东西就返回 hasNewContent 为 false。

[node types]
claim 一个核心断言，一句话说完，有主语、有结论、有条件
mece 一组并列或递进的因素，至少两项，互不重叠
example 一个能替代抽象解释的具体例子
contrast 两个易混概念的区别，必须点明差异维度
pitfall 一个常见错误理解，要写清错误本身
question 这一步没解决、留着的具体问题
formula 公式或伪代码，要带变量说明

[user]
【本场主题】{{topicTitle}}
【当前节点】{{nodeTitle}}

【已有笔记】
{{existingNoteBlocksAsPlainList | 没有则写"（空）"}}

【本段对话】
用户：{{userTurn}}
助手：{{assistantTurn}}

【用户导入的资料片段】
{{relevantChunks | 没有则整段省略}}

请只输出 JSON，不要任何解释文字。格式：
{
  "hasNewContent": true|false,
  "blocks": [
    {
      "blockType": "claim|mece|example|contrast|pitfall|question|formula",
      "content": "正文，用连贯段落，禁止项目符号",
      "groundedIn": "conversation | document:3 | inference",
      "isNewRelativeToExisting": true
    }
  ],
  "nodeAction": "create | update | none",
  "nodePatch": { "title": "", "masteryDelta": 0 },
  "edges": [ { "toNodeId": "", "type": "parent|prereq|related" } ],
  "discarded": [ { "reason": "重复已有 | 元话语 | 无依据数字 | 无新信息" } ]
}
```

**关键设计**：要求模型显式输出 `discarded` 字段，说明它丢掉了什么、为什么丢。这既是一个自我检查机制（强迫模型解释），也是调试时最有用的信号——如果 `discarded` 里大量出现"无新信息"，说明触发太频繁；如果从来没出现过，说明模型在凑数。

**输出校验**：用 zod 校验返回的 JSON。校验失败或模型不返回合法 JSON 时，重试一次（把校验错误附回去）；再失败则把该次 `extractions.status` 记为 `failed`，写入 `error`，**不修改任何已有数据**。

### 4.6 落库规则

```
if (!hasNewContent || blocks.length === 0)
    → extractions.status = 'skipped'，什么都不写
else
    → 对每个 block：
        若 content 与该节点已有 block 的相似度 > 0.9（用 FTS5 或简单字符重合度）
            → 跳过，记入 discarded
        否则 → 插入 note_blocks，ordinal 递增，写入 origin_turn_id
    → 若 nodeAction === 'create'：先建 node（需要 topic_id 和 kind）
    → 若 edges 非空：插入 edges，去重靠 UNIQUE(src_id, dst_id, type)
    → extractions.status = 'ok'，payload_json 存完整返回
```

**幂等性**：同一个 `turn_id` 重复抽取必须产生相同结果，不能重复插入。`extractions` 表按 `turn_id` 查已有记录，若状态为 `ok` 则直接跳过。

### 4.7 笔记怎么做到"美观、看得进去"

这一节是排版规范，直接决定产品观感。

**卡片结构**（固定，不允许自由发挥）：

```
┌──────────────────────────────────────────────┐
│  softmax 为什么要减去最大值           ●●○○○  │ ← 标题：一句话，最多 30 字
│  问题 · 已收线 · 3 天前                        │ ← 元信息行
├──────────────────────────────────────────────┤
│  ▍核心                                          │ ← 类型标签，带颜色条
│  指数函数在参数很大时会溢出，减去最大值后         │
│  最大项变成 1，其余都小于 1，因而不溢出。         │ ← 正文：连贯段落，无符号列表
│  这个操作不改变结果，因为分子分母同时缩小了       │
│  相同的倍数。                                   │
│                                                │
│  ▍对比                                          │
│  减去最大值和除以总和是两件事：前者只为防溢出，    │
│  后者才是归一化本身。                            │
│                                                │
│  ▍留着的问题                                    │
│  如果某一项本身是无穷大，这个技巧还有效吗？        │
├──────────────────────────────────────────────┤
│  [从哪来] 注意力机制是怎么回事  [看原文]          │ ← 溯源行，永远可点
└──────────────────────────────────────────────┘
```

**排版硬规则**：

1. **正文必须是连贯段落，禁止 `•` `-` `*` 项目符号。** 这条与全局排版约束一致（§8.1），在笔记里尤其重要——符号列表是"AI 味"最强的视觉信号。
2. **`mece` 类型例外**：允许用 `1. 2. 3.` 编号，因为它本身就是有序步骤。但仍然禁止符号列表。
3. **每条正文控制在 120 字以内。** 超过说明这条该拆成两条。
4. **类型标签用不同颜色条**，`claim` 用主色，`contrast` 用蓝，`pitfall` 用红，`question` 用灰。这给卡片一个可扫视的节奏。
5. **一张卡片最多显示 3 条笔记块，超出折叠**，显示「还有 2 条」。默认展开的是 `claim` 和 `pitfall`。
6. **卡片默认高度不超过 260px。** 这是为了让右侧栏能在不滚动的情况下看到 2 张卡片。宁可折叠，不要撑长。
7. **绝对不要出现"AI 生成"的痕迹**：禁止 emoji 装饰、禁止"✨""💡"这类图标、禁止"让我们来看看"这类过渡句。

**为什么这些细节重要**：用户看笔记的动机是"复习"，如果卡片看起来像一堆自动生成的文字，他第二次就不会再打开。**笔记的观感直接决定这个功能有没有人用。**

### 4.8 笔记的两个视图

**右侧栏（对话时看）**：只显示本场产生的卡片，按时间倒序，新卡片带一个 0.3 秒的淡入动画。用户可以不打断对话地扫一眼。

**笔记页（专门看）**：左侧栏点进去。布局是两栏，左边是节点树（按 `parent` 边组织的可折叠树），右边是选中节点的完整卡片，包括被折叠的笔记块。顶部有筛选：按类型、按掌握度、按时间、只看未收线。

### 4.9 用户参与

- 每条笔记块右上角有「改」和「删」。用户的手改**优先级最高**，模型后续更新不得覆盖 `user_note` 类型和用户手工编辑过的内容（加 `edited_by_user` 标记）。
- 卡片底部有「让 AI 重讲」「让 AI 出个题」两个按钮。
- 用户可以在对话里说"把这个记下来"，AI 必须无条件创建一个节点并写入用户说的内容为 `user_note`。

### 4.10 验收（对抗性测试集）

**必须用这些用例验证，全部通过才算完成。** 它们专门设计来抓废话：

| # | 输入 | 期望 | 反例（出现即失败） |
|---|---|---|---|
| 1 | 用户说"谢谢" | `hasNewContent: false`，不产生任何笔记 | 产出"用户表示感谢" |
| 2 | AI 回复里全是"这是个好问题，让我们来看看……" | 抽取结果为 `none`，或只留一个 `question` | 产出 claim |
| 3 | 同一轮对话抽取两次 | 第二次 `skipped`，数据库无重复行 | 产生两条一样的块 |
| 4 | AI 随口说"大概快十倍" | 不进 `claim`，或进 `question` 并标注存疑 | 写成"速度快十倍" |
| 5 | AI 讲了 400 字的解释 | 笔记正文 ≤ 120 字，且不丢关键条件 | 把 400 字原样搬进笔记 |
| 6 | 连续 5 轮都在讲同一个点 | 只产生 1 个节点、1 到 3 条块 | 产生 5 个节点 |
| 7 | 用户导入一份 PDF 问"第 3 页说了什么" | 产出 `source_quote`，带页码 | 转述且不标页码 |
| 8 | 任何一次抽取 | 正文中不含项目符号 | 出现 `-` 或 `•` |
| 9 | 任何一次抽取 | 正文中不含元话语 | 出现"本段讨论" |
| 10 | 抽取期间断网 | `extractions.status = 'failed'`，对话不受影响，可重试 | 崩溃或数据损坏 |

## 5. 归航与未收线（待实现）

### 5.1 要解决的问题

用户从"注意力机制"出发，一路问到"浮点数的二进制表示"，中间过了 4 层。三天后他回来，需要知道：这条线走到哪了、最初那个问题回答了没、从哪接着走。

### 5.2 收线判定

**触发**：用户点「今天到这儿」，或会话闲置超过 20 分钟。

**调用**：用 `utilityModel`，输入是本场所有 `status = 'open'` 的节点及其祖先链，加上这些节点的笔记块摘要。

```
[system]
你在判断学习者的几条支线是否已经走完。

判断标准：一个支线算走完，当且仅当它最初想问的那个问题，
在对话里已经被明确回答了，而且答案不是含糊的。

回答含糊的几种表现，遇到这些一律算没走完：
只说了一个名词没有解释它是什么；
用了"差不多""一般来说""大概"这类词；
答案在对话里被提出但没有被确认。

[user]
【支线一】
最初的问题：{{rootQuestion}}
路径：{{path}}
相关笔记：{{noteSummaries}}

【支线二】
...

请只输出 JSON：
{
  "threads": [
    {
      "rootNodeId": "",
      "isClosed": true|false,
      "conclusion": "如果已收线，用一句话写清结论",
      "stoppedAt": "如果没走完，写清停在哪个具体问题上",
      "nextStep": "如果没走完，写清下次从哪继续"
    }
  ]
}
```

**落库**：`isClosed` 为真时把该支线根节点 `status` 改为 `gathered`，把 `conclusion` 写入该节点 `body_md` 的结论区，并创建一条 `answers` 边；为假时保持 `open`，把 `stoppedAt` 和 `nextStep` 写进该节点的 `note_blocks`（类型 `question`）。

### 5.3 未收线清单的排序

不是按时间，而是按"现在最该接着学"排序。评分公式（可调）：

```
score = 0.4 * recency      (最近 7 天内碰过得满分，线性衰减)
      + 0.3 * blocker      (这条线是其他未完成节点的 prereq，是则满分)
      + 0.2 * gap          (掌握度越低分越高，1 - mastery/5)
      + 0.1 * openAge      (开着越久分越高，但超过 30 天开始衰减)
```

**只显示前 5 条。** 多余的收进「全部」按钮。**这一条是硬要求**：未收线会有几十条，全列出来会变成永远做不完的作业，用户会因为这个功能而放弃使用软件。

每条给出三个出路：继续、我懂了（关掉）、不感兴趣（关掉并降低同类推荐权重）。**"不感兴趣"必须存在**，能主动放弃的清单才不是心理债。

## 8. 全局约束（所有子系统都要遵守）

### 8.1 排版约束（来自用户的明确要求，最高优先级）

**这一条适用于：对话回复、笔记正文、小结、复习出题、以及所有 AI 生成并展示给用户的文字。**

- 严禁使用 `•` `-` `*` 这类符号开头的项目符号列表。
- 日常讲解一律写成连贯段落。需要分点时说"第一……然后……最后……"，不要另起一行打符号。
- 只有真正的操作步骤、配置清单、代码参数才编号，用 `1. 2. 3.`。
- 严禁"作为AI""很高兴为您服务""希望以上回答对您有帮助"这类套话，不要客套开场，直接说内容。
- **提示词自身也必须遵守这条**，不能在提示词里用符号列表给模型做反面示范。

**实现方式**：这段约束已经写死在 `src/main/server.ts` 的 `SYSTEM_PROMPT` 里。**新增的每一个提示词（抽取、归航、出题、文档问答）都必须包含这一段**，建议抽成一个共享常量 `FORMAT_RULES` 拼接复用，避免各处不一致。

**已有自动化断言**（`scripts/e2e.cjs`）：检查系统提示词里包含 `•`、`不要用`、`连贯的段落`、`第一`、`最后`、`1. 2. 3.`、`作为AI`、`套话`，并且提示词自身没有以符号开头的行。新增提示词后要同步加断言。

### 8.2 密钥与隐私

密钥只在主进程内存和加密存储中出现，永远不返回渲染进程。用户的对话和文档内容只发给他自己选定的服务商，不发往任何其他地方。所有文件都存在本地 `userData` 目录。

### 8.3 数据完整性

- `turns` 只追加，永不修改。
- 所有派生物（nodes、edges、note_blocks、summaries）必须可重算。设置页提供「重算（保留现有卡片）」与「重算并允许重新分卡」两个入口。
- 任何后台任务失败都不得影响对话，也不得破坏已有数据。
- 每次 schema 变更必须写迁移，不能重建表。

### 8.4 测试隔离（血泪教训）

**验证脚本绝对不能碰用户的真实数据目录。** 应用支持 `ZHITU_DATA_DIR` 环境变量重定向数据目录；`scripts/verify.ps1` 必须把数据目录指到 `%TEMP%\zhitu-verify-data`，并在跑完后对比真实数据库哈希证明没被改动。

`scripts/e2e.cjs` 里有两条断言守着这件事：检查运行在沙箱里、检查沙箱不在真实目录下。**这两条断言不能删。** 早期版本没有这个隔离，把用户配好的密钥和聊天记录冲掉过。

## 9. 新需求一：文档导入与处理

### 9.1 目标

用户可以把 PDF、图片、PPT、Word、Excel、Markdown、代码文件直接拖进对话栏，然后针对它提问。文档内容要能进入笔记（作为 `source_quote` 类型），并且笔记上能回指到具体页码。

### 9.2 交互设计

**入口三个，全部支持**：

1. 输入框左侧一个回形针图标，点击开文件选择框
2. 直接把文件拖进输入框区域（整个 mid 面板响应拖放，拖入时显示一层虚框覆盖和"松手就加进来"提示）
3. 粘贴板里的图片，直接 Ctrl+V 粘进输入框

**附件在对话里的呈现**：用户发送的那条消息上方，显示附件小卡片，含文件类型图标、文件名、页数/大小。**不要显示缩略图大图**，那会撑乱对话流。

**附件作用域**：默认只对"当前这一场"有效。输入框上方显示已挂载的附件 chip，每个 chip 带 × 可以移除。**附件内容不自动进入全局上下文**，只有用户明确问到、或检索命中时才送入模型。

### 9.3 处理管线

```
用户拖入文件
  → 计算 sha256，查重（同一场内重复文件直接复用已有记录）
  → 原件拷贝到 userData/attachments/<sha256 前2位>/<sha256>.<ext>
  → 写 attachments 行，extract_status = 'pending'
  → 立刻返回界面（不阻塞，卡片显示"正在解析…"）
  → 后台异步提取（见下表）
  → 提取出的文本切块写入 chunks
  → extract_status = 'ok' | 'partial' | 'failed'
```

**提取策略表**（**每一项动手前先做 30 分钟可行性验证**，标记为「待验证」的不要直接进正式实现）：

| 类型 | 方案 | 状态 |
|---|---|---|
| `txt` `md` `csv` `json` `代码` | 直接读文本，按平台编码检测（先试 UTF-8，失败试 GBK） | 待实现 |
| `html` | 剥离标签取正文 | 待实现 |
| `pdf`（文字版） | `pdfjs-dist` 逐页抽文本 | 待验证 |
| `pdf`（扫描版） | 逐页渲染成 PNG，交给视觉模型 OCR | 待验证，成本较高，先只做文字版并明确告诉用户 |
| `docx` | `mammoth` 转 HTML 再转 Markdown | 待验证 |
| `pptx` | 抽 XML 里的文本（`<a:t>` 节点），**注意这拿不到图表内容** | 待验证 |
| `xlsx` | `node-xlsx` 或 `exceljs` 转成 CSV | 待验证 |
| `图片`（png/jpg/webp） | 直接作为视觉输入送给模型，不做本地 OCR | 待实现 |

**关于 PPT 的重要提醒**：只抽文本会丢掉所有图表和排版信息，而 PPT 的信息往往恰恰在图里。所以对 PPT 和扫描版 PDF，**优先方案是渲染成图片交给视觉模型**，文本抽取只作为兜底。这需要在设置里加一个开关，因为视觉输入贵得多。

**视觉模型的接入方式**：OpenAI 兼容协议的 messages 里，用户消息的 `content` 可以是一个数组，元素形如 `{type:'text', text:'...'}` 或 `{type:'image_url', image_url:{url:'data:image/png;base64,...'}}`。实现时要检测当前服务商和模型是否支持视觉，不支持时降级为文本抽取并在界面提示用户。

### 9.4 检索而非全塞

一份 50 页的 PDF 有 10 万字，**绝不能整个塞进上下文**。做法：

1. 提取后切成 300 到 500 字的块，写入 `chunks`
2. 用户提问时，用 FTS5 对 `chunks.text` 检索，取最相关的 3 到 5 块
3. 只把这 3 到 5 块送入模型
4. 要求模型在回答里标注引用页码，格式为 `[第 3 页]`

**v2 先用 FTS5（trigram 分词器，支持中文）。** 不要一上来做向量检索。等检索质量真的成为瓶颈，再在 `search_fts` 旁边加 `sqlite-vec`，接口保持一致。

### 9.5 文档内容怎么进笔记

当模型的回答基于文档内容时，抽取任务要把对应切片一起送进去，并要求产出 `source_quote` 类型的笔记块，正文是**原文引用**（不是转述），并带页码。

**衔接的两个关键设计**：

**第一，导入的文档本身要成为一个节点。** 用户在某个主题下第一次用到某个附件时，自动创建一个节点，`kind = 'resource'`，标题是文件名，`body_md` 写一句这份资料是什么。所有来自这份文档的引用块都挂在这个节点下。这样做的原因是：**否则引用会散落在各个问答节点里，用户想看"这份 PDF 我都学到了什么"时找不到入口。**

**第二，传参方式要让模型能正确指认来源。** 给模型的切片不能只给文本，必须带序号，且序号要和 `chunks.ordinal` 对应：

```
【用户导入的资料片段】
[片段 1 · 第 3 页] 指数函数在数值计算中容易溢出，因为……
[片段 2 · 第 5 页] 减最大值是一种常见的数值稳定化技巧……
```

抽取返回的 `groundedIn` 字段写成 `document:1`（指片段 1，而不是页码），落库时把片段 1 反查成 `chunk_id` 写进 `origin_chunk_ids_json`。**不要让模型直接写页码**，它数不清楚，会写错。

**第三，卡片上显示来源。** `source_quote` 类型的块底部显示「来自《文件名》第 3 页」，点击直接跳到文档预览的对应位置。文档预览页显示原件（PDF 用 iframe 或 `<embed>`，图片直接 `<img>`，其他格式显示提取出的文本）。

### 9.6 新增接口

```
POST /attachments                   → multipart 上传，返回 attachment 记录（立即返回，后台解析）
GET  /attachments/:id               → 状态与元信息
GET  /attachments/:id/chunks        → 切片列表（用于预览和调试）
GET  /attachments/:id/file          → 返回原件二进制（供预览页使用）
GET  /sessions/:id/attachments      → 本场附件列表
DELETE /attachments/:id             → 删除附件与切片（同时清理磁盘文件）
POST /documents/search              → {sessionId, query, limit} → 返回相关切片
```

### 9.7 安全与限制

单文件默认上限 50 MB，单场附件数上限 20。可执行文件（`.exe` `.dll` `.bat` `.ps1`）**拒绝导入**，明确提示用户。解析在后台进行，**必须防住恶意或损坏文件导致的崩溃**：每个解析任务套 try/catch 和超时（30 秒），失败只写 `extract_error`，不影响其他功能。

## 10. 新需求二：去掉"新手还是老手"的问题

### 10.1 改动

- 首次向导从三步减为两步：**第 1 步选服务商，第 2 步填密钥并测试连接**。删掉"你现在的水平大概是"这一步。
- `LEVEL_LABELS` 和 `settings.learnerLevel` 保留在数据库里以兼容已有数据，但**不再在界面上询问**，也不再拼进系统提示词。

### 10.2 替代方案：行为推断

新建 `learner_profile` 表（见 §1.3），初始 `level_estimate = 1`、`confidence = 0`。每轮对话后由 `utilityModel` 打一次标签，更新信号计数：

| 信号 | 含义 | 对 level_estimate 的影响 |
|---|---|---|
| 问"XX 是什么" | 缺乏基础词汇 | 负向，-0.1 |
| 用了专业术语且用法正确 | 有基础 | 正向，+0.2 |
| 要求"举个具体例子" | 抽象理解有困难 | 负向，-0.1 |
| 追问边界条件（"什么情况下不行"） | 理解较深 | 正向，+0.3 |
| 指出 AI 的错误 | 有独立判断 | 正向，+0.4 |
| 连续三轮问同一层次的问题 | 卡住了 | 负向，-0.2 |

`level_estimate` 限制在 0 到 5，`confidence` 随样本数增长（`1 - exp(-n/20)`）。

### 10.3 怎么用这个推断

**只在 `confidence > 0.5` 时才影响提示词**，且只影响一句：

```
根据你之前的提问方式判断，这个人的基础大约在「{{levelLabel}}」这一档。
解释时可以按这个深度来，但不要说出来，也不要假设他不知道某个具体的词。
```

置信度低时**完全不注入这一句**。宁可没有画像，也不要给一个错的画像。

**给用户一个出口**：设置页保留一个「讲解深度」滑块（少解释 / 适中 / 多解释），默认"适中"，用户想手动控制时可以调。这比问"你是新手吗"体验好得多——它问的是**他想要什么**，而不是**他是什么水平**。

## 11. 新需求三：API 配置持久化

### 11.1 现状与改动

现在其实**已经是**这个行为：`app_config` 里的 `settings` 是持久的，重启后自动复用。要做的是把它做得更可靠、更明显：

1. **启动时校验**：引导流程只在 `settings.onboarded === false` 时出现。已完成引导的用户，直接进主界面。
2. **密钥失效的检测与提示**：对话返回 401 时，除了在对话区显示错误，还要在界面顶部显示一条常驻提示条「API 密钥可能已失效，去设置检查」，带一个直接打开设置弹窗的按钮。**这条提示只有用户点掉或测试连接成功后才消失。**
3. **设置页显示当前状态**：明确显示"当前使用：DeepSeek · deepseek-chat"，让用户一眼知道自己在用什么。
4. **支持多套配置并存**（可选，优先级低）：允许用户保存多个服务商配置，用下拉切换。如果做，新增 `provider_profiles` 表；如果不做，至少要让切换服务商时不用重新填密钥（按 `providerId` 分别存密钥）。
5. **换服务商时不清空旧密钥**：`secret.apiKey` 按 `providerId` 分开存，键名 `secret.apiKey.<providerId>`。切回来时自动带出。

## 12. 新需求四：界面完善

### 12.1 现状盘点

已经有的：左侧栏（品牌、新的一场、当前场次、设置入口）、中栏（标题、模式切换、对话流、输入框、空状态）、右栏（本场记下的点、未收线，目前是占位）。

**明显缺失的**：左侧没有历史场次列表（只有"当前"一个），没有全局搜索，没有笔记页，没有地图页，没有导出入口，没有键盘快捷键，输入框不支持附件。

### 12.2 导航结构

改成四个主页面，用左侧栏切换，**不做多级菜单**：

```
左栏：织图
  ＋ 新的一场
  ─────────────
  💬 对话        ← 默认
  📝 笔记        ← 新增
  🗺 地图        ← 新增

  ─────────────
```

**为什么要加"最近的学习"**：这是解决"三天后回来不知道从哪继续"的第一入口。用户打开软件第一眼就该看到"上次你在聊这个"。

### 12.3 视觉规范

**当前色调已经定了，沿用**：

```
背景 #fbfaf8    面板 #f5f3ef    卡片 #ffffff
主线 #e6e2da    强调线 #d5d0c6
正文 #2b2926    次要 #5d5852    弱化 #938c82
主色 #2f6f5e（墨绿）  主色浅底 #e8f0ec
危险 #a8402f    危险浅底 #fbeeeb
圆角 10px / 7px    字体 系统默认（含 PingFang SC / Microsoft YaHei）
```

**要补的视觉细节**：

1. **深色模式**。用 `prefers-color-scheme` 自动跟随，或设置里手动切。深色下主色改为 `#4a9b85`，背景 `#1c1b19`，卡片 `#242320`。**必须保持对比度 ≥ 4.5:1。**
2. **对话区的阅读宽度限制在 720px**，已经做了，保持。宽屏上文字横跨整个窗口是最常见的阅读体验杀手。
3. **流式输出时的光标**已有，保持。
4. **加载状态分级**：小于 300ms 不显示任何 loading（避免闪烁）；300ms 到 3 秒显示光标或骨架；超过 3 秒显示"正在想…"加一个停止按钮。
5. **空状态要有引导性文字**，不能只写"暂无数据"。每个空状态都要告诉用户下一步能做什么。
6. **过渡动画不超过 200ms**，且只用 opacity 和 transform，不要做位移和缩放的花哨效果。第三方动效库一律不引入。

### 12.4 建议新增的功能（按优先级）

**优先级高，建议做**：

1. **全局搜索（⌘K / Ctrl+K）**：一个命令面板，能搜节点、笔记、对话原文，也能直接执行命令（"新的一场""打开设置""导出"）。基于 FTS5 实现。
2. **导出**：导出全部笔记为 Markdown（每个节点一个文件，`[[双链]]` 保留，能直接导进 Obsidian）；导出单场对话为 Markdown；导出全部数据为一个 JSON 包（用于分享和备份）。
3. **键盘快捷键**：`Ctrl+N` 新的一场、`Ctrl+K` 搜索、`Ctrl+/` 打开快捷键列表、`Esc` 关闭弹窗、`Ctrl+Enter` 强制发送（`Enter` 发送已经是默认）。
4. **最近学习入口**（见 §12.2）。
5. **本场小结卡片**：会话结束时在对话流末尾插入一张小结卡，含本场搞懂了什么、还开着什么、下次从哪继续。这是 §5 归航的呈现方式。

**优先级中，看情况做**：

6. **专注模式**：隐藏左右两栏，只留对话区，适合长时间阅读 AI 的长回答。顶部一个按钮切换。
7. **笔记大纲**：在笔记右键加一个目录，快速跳到某个节点。
8. **统计页**：本周学了什么、产出了多少笔记、哪些节点还没收线。**不要做成打卡和连续天数**，只呈现事实，不做激励。
9. **多主题支持**：允许同时存在"学 AI""学英语"等多张独立的地图，顶部一个下拉切换。

**明确不做**：

- 账号系统、云同步、手机 App、社区、分享广场、排行榜、打卡、成就徽章、音效、本地模型内置、自动抓取网页。

### 12.5 界面验收方式

**每个界面改动都必须截图给人看。** 仓库里有 `scripts/screenshot.cjs`，它启动真实窗口，用 `webContents.capturePage()` 把界面存成 PNG 到 `%TEMP%\zhitu-shots`。

**为什么截图是必须的**：自动化测试只能检查 DOM 元素存不存在。曾经有一次，向导第一步的卡片高度是 803px 而窗口只有 801px，顶部被切掉了，**所有测试全绿**——因为 DOM 确实都在。这个问题是截图才发现的。所以界面相关的改动，跑完 `verify.ps1` 之后**必须再截图看一眼**。

## 13. 实施顺序

严格按这个顺序做，每一步都要跑通验证再进下一步。**不要并行开发多个子系统**——笔记质量不行的话，地图画得再漂亮也没有内容可显示。

**第 0 步：清除向导第三步 + 首次进入的开始卡片**

这是最小改动、最快见效的一步，先做它。删掉"你的水平"这一步（见 §10），把首次进入的空白页换成 §3.0 的开始卡片。做完这一步，你自己用起来就已经顺很多了。

**第 1 步：实时笔记（最高优先级，决定产品成败）**

顺序是：先做 `note_blocks` 和 `chunks` 表的迁移，然后做 §4.5 的抽取调用和 §4.10 的十条对抗性测试，最后做 §4.7 的卡片渲染。**必须先让十条对抗性测试全过，再去调 UI。** 因为如果抽取质量不行，卡片样式再好看也是包装废话。

验收：手动聊 20 轮真实的学习对话，把自己当成用户读一遍卡片，判断"我三天后回来看这些，能不能想起我学过什么"。

**第 2 步：文档导入**

先做 `txt`/`md`/`code` 和图片（最简单、最快见效），再做 PDF，最后做 Office 系列。视觉模型接入放在 PDF 之后。

**第 3 步：归航与未收线**

依赖第 1 步产出的节点和笔记。

**第 4 步：笔记页**

把卡片从右侧栏扩展成一个完整的页面。

**第 5 步：地图**

依赖足够多的节点才有意义。节点少于 20 个时地图没什么可看的。

**第 6 步：复习 + 导出 + 搜索**

复习依赖掌握度数据积累，放在后面。

**第 7 步：界面打磨**

深色模式、动画、快捷键、空状态。放在最后，因为前面每一步都可能改变界面结构。

| 第 5 步 | 验证 50 个节点时地图仍能渲染且不卡（用 `performance.now()` 计时） |
| 第 6 步 | 验证导出的 Markdown 能被重新解析回来（round-trip） |
| 第 7 步 | 每个界面截图人眼确认 |

**联网验证**（会花少量 API 费用，不进 CI）：

```bash
npm run prompt-check
```

用真实服务商发问题，检查回答里有没有符号列表、套话、超长。**新增任何提示词后，都要扩展这个脚本覆盖它。**

## 15. 明确不做的事

写在这里是为了将来有人（包括实现者自己）提起来时，有明确答复。

| 不做 | 原因 |
|---|---|
| 账号系统、登录 | 单机软件不需要 |
| 云同步 | 导出文件分享就够了 |
| 手机 App | 界面要重做一遍，成本翻倍 |
| 内置本地模型 | 安装包会变成几个 G，朋友下载不下来 |
| 社区、分享广场 | 这是自用工具，不是平台 |
| 排行榜、打卡、成就徽章 | 把学习变成刷数据，长期有害 |
| 音效、庆祝动画 | 与「界面要安静」的原则冲突 |
| 自动抓取网页和视频 | 是另一个产品 |
| 内置课程内容 | 我们提供地图和引导，内容由 AI 现场生成 |
| 任何形式的项目符号列表出现在 AI 输出里 | 用户的明确要求，见 §8.1 |

## 16. 给实现者的最后提醒

**这个产品的价值不在技术栈上。** Electron、SQLite、Hono、React 全是标准件，网上教程遍地，不会成为风险点。真正的风险只有两个：**抽取提示词能不能稳定判断出"什么值得记"**，以及**归航判断会不会过度打扰用户**。

所以：把大部分精力花在 §4 和 §5 的提示词上，用 §4.10 的对抗性用例反复捶打它们。界面可以丑一点，笔记不能是废话。

还有一条：**任何声称"改好了"的结论，都必须有可复现的证据。** 这个项目已经出现过三次假通过——验证脚本因为单实例锁自己退出却报成功、检查项为零却显示通过、检查通过但详情写着失败原因。每次都差点把问题带进发布。所以写断言的时候，**要同时验证"通过时会显示什么"**，不要只写判断条件。
