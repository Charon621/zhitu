## 项目是什么

一个叫「织图」的学习系统。它不是聊天软件，是「一块不会被擦掉的黑板，黑板自己长成一张地图」。

用户跟 AI 对话学习，系统在后台悄悄把每次学到的东西萃取成结构化的笔记，时间久了这些笔记连成一张知识地图。它要解决的核心问题是：用户从一个点发散到很远的地方之后，怎么还能找回来，怎么还能看到自己学过什么。

产品意图的完整描述在规格文档第 0 节。**那里有一张表，把用户的每一句原话对应到了具体设计，任何实现决策都不能偏离它。**

## 用户是谁，他怎么跟你协作

他是产品经理，不懂编程，同时是这个软件的第一个用户。你的分工是：他负责判断「这样对不对、好不好用」，你负责实现和验证。

有几条他明确要求过的工作方式：

**关于说话。** 跟他对话时**绝对不要用 `•`、`-`、`*` 这类项目符号列表**，要写成连贯的段落，需要分点就用「第一……然后……最后……」连起来。只有真正的操作步骤才用 `1. 2. 3.` 编号。不要用「作为AI」「希望对你有帮助」这类套话，直接说内容。这不是风格偏好，是他对 AI 输出最反感的一点——**这个要求同样写进了软件的提示词里，所以你写的任何新提示词都必须包含这条约束。**

**关于决策。** 涉及产品取舍的事情（比如某个功能要不要做、某个交互该怎么样），先问他，给他选项和你的推荐，不要自己拍板。纯技术实现细节你自己决定，不用问。

**关于节奏。** 一次做一小步，每步都要能跑起来、能验证、能交付一个安装包给他试用。不要憋一个大的然后一次性交出来。

**关于诚实。** 做不了就说做不了，验证不了就说验证不了。**最让他恼火的不是 bug，是我声称"改好了"但实际没有验证。** 见下面第四节。

## 工作规则

### 一、验证不是可选项

仓库里有一套自动化验证，改完任何东西都要跑：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\verify.ps1
```

它会启动三次真实的程序，并跑流式协议、笔记对抗、附件地基三组离线检查，当前合计 389 项（各阶段预期数字硬编码在脚本顶部，随功能增长而增加）。**这些检查在你改完之后必须仍然是全绿的**，绿了才能说"做完了"。

新增功能要新增对应的断言。规格文档第 14 节有每一步该新增什么验收的表。

### 二、验证脚本绝对不能碰用户的真实数据

这一条是用真实损失换来的。应用的验证脚本支持一个 `ZHITU_DATA_DIR` 环境变量来重定向数据目录，`verify.ps1` 必须把它指到 `%TEMP%\zhitu-verify-data` 沙箱里。

**早期版本没做这个隔离，把用户配好的 API 密钥和聊天记录冲掉过，不可恢复。** `scripts/e2e.cjs` 里有两条断言守着这件事，不要删。

跑完验证后可以核对真实数据没被动过：

```powershell
Get-FileHash "$env:APPDATA\zhitu\zhitu.db"
```

### 三、这个项目已经出现过三次「假通过」，你要防住

每一次都差点把问题带进发布，所以我把它们写出来。

**第一次**，验证脚本全绿但我不知道它一项都没跑。原因是程序被单实例锁挡住后自己退出了，**而退出码是 0**，调用方只看退出码就以为成功。修法是让调用方以「检查项数量」为准，不只信退出码。

**第二次**，同样的问题换了张脸：三项检查都显示通过，但详情栏写着失败原因。原因是我把详情文字无条件传给了断言函数，不管真假都显示。修法是按结果分别给详情。

**第三次**，界面上向导卡片的实际高度是 803px 而窗口只有 801px，顶部被切掉了，**所有测试全绿**——因为 DOM 元素确实都在，只是被窗口裁掉了。这个是靠截图才发现的。

所以，**你写断言的时候要同时想清楚「通过的时候它会显示什么」**。一条通过的检查如果显示着吓人的文字，或者一条检查实际跑了零项，都比没有检查更危险，因为它会让你相信一个假结论。

界面相关的改动，跑完验证之后**必须截图看一眼**：

```powershell
& "node_modules\electron\dist\electron.exe" "scripts\screenshot.cjs"
```

图片在 `%TEMP%\zhitu-shots`。你可以用读图工具自己看，也可以让我看。

### 四、有一个检查需要花钱，不要随便跑

```bash
npm run prompt-check
```

它会用用户真实的 API 密钥发请求给 DeepSeek，验证提示词在真实模型上是否生效。**会花掉他极少量的钱。** 自动化的 e2e 测试用的是本机假 AI 服务，不花钱也不联网。所以日常验证用 `verify.ps1`，要验证提示词效果时才用 `prompt-check`，用完告诉他花了多少。

### 五、改动了什么要告诉他，尤其是坏消息

每轮结束时说清楚三件事：改了什么、怎么验证的、有没有他需要知道的问题。**如果搞坏了什么，第一时间说，不要藏。** 这个项目里我已经如实报告过两次自己造成的损失，他接受坏消息的能力比你想的强，但受不了被瞒着。

### 六、几个不要做的事

不要写打卡、徽章、排行榜、成就音效这类东西，规格文档第 15 节列了完整的「不做清单」。不要引入符号列表。不要为了显得功能多而做没人用的功能。不要在没验证的情况下说「应该没问题」。

### 七、提示词的排版约束要复用

规格文档第 8.1 节那段排版约束，**新增的每一个提示词都必须包含**。建议抽成一个共享常量 `FORMAT_RULES` 拼接复用，避免各处不一致。现在 `scripts\e2e.cjs` 里有六条断言检查它，新增提示词后要同步加断言。

## 附：给你（产品经理）自己的备注

这段话**不要**发给 AI，是给你自己看的。

**为什么要强调那三条工作规则。** 上面第三节那三次假通过、第二节那次数据丢失，都不是理论风险，是这几天真实发生的事。写进去是为了让接手的 AI 一上来就知道边界在哪，而不是重蹈覆辙。

**如果他第一轮就急着写代码。** 让他停下来先回答理解。一个没读懂规格就动手的 AI，改出来的东西多半要返工，而返工比慢一点更贵。

**如果他说某个需求做不了。** 追问他具体卡在哪，是技术限制还是他没想到办法。技术限制是真实存在的（比如 PPT 里的图表确实很难完整提取），但一个含糊的「做不了」通常意味着他没想清楚。

**验收清单**（每次他交东西给你，看这几条）：

第一，安装包给你了没有，你能不能装上并打开。第二，他说验证通过，你要问清楚跑的是哪个脚本、多少项检查。第三，如果是界面改动，让他截图给你看。第四，如果提示词改了，让他说明改了什么、为什么改。
