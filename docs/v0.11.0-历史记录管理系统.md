# 织图 v0.11.0：历史记录管理系统（设计稿）

## 1. 一句话目标

把现在的「学习记录」弹窗，升级成一套**找得回、理得清、删得放心**的历史系统：
任何一场学习都能在三秒内找到；删除永远可以后悔；一个主题下的一场场学习能连成脉络，而不是一条越堆越长的流水账。

### 2.2 缺什么（这一版要补的）

| # | 缺口 | 依据 | 用户的感受 |
|---|---|---|---|
| 1 | **只能看到最近 50 场** | `listSessions(limit=50)`、`listArchivedSessions(limit=50)`，`GET /sessions` 没有任何分页参数 | 第 51 场之后从界面上消失（数据还在库里） |
| 2 | **筛选只有标题一个维度** | `Chat.tsx:896` 只做 `title.toLowerCase().includes(query)` | 想找"上周没学完的那场"只能靠翻 |
| 3 | **列表信息太少** | 每行只有标题和时间（`Chat.tsx:914-916`） | 看不出这场有几轮对话、记了几条笔记、有没有未收线 |
| 4 | **删除不可撤销** | 弹窗自己写着"这一步不能撤销"（`Chat.tsx:958`），删完直接 CASCADE（`store.ts:267-299`） | 手一抖就没了，只能靠备份 |
| 5 | **归档是死胡同** | 归档后只能从弹窗底部展开（`Chat.tsx:930-948`），没有独立管理视图，也没有自动归档 | 归档 ≈ 遗忘 |
| 6 | **主题维度丢失** | 历史列表是平铺的场次（`store.ts:145`），不看 `topic_id` | "AI 入门"学了 12 场，看不出这 12 场的先后 |
| 7 | **资料场次混进历史** | 资料库每导入一份文件就建一个主题 + 一场（`server.ts:663-667`） | 导 10 本书，历史里多 10 条"资料学习" |
| 8 | **没有批量操作，也没有占用视图** | `attachments.bytes` 存了但没有任何地方汇总 | 想清空间只能一场一场删 |
| 9 | **搜索与历史是两套** | ⌘K 搜内容不搜场次；历史弹窗搜标题不搜内容 | 记得内容却找不到是哪一场 |
| 10 | **主题名拿不到** | `GET /sessions` 返回 `SELECT *`，有 `topic_id` 但**没有主题名**，也没有 `/topics` 路由（`store.ts:145-149`、`server.ts:473`） | 任何"按主题看历史"都得先扩这个接口 |
| 11 | **主题级管理是半成品** | `topics.archived_at` 列存在且被地图过滤（`db.ts:30`、`store.ts:164`），但全仓没有任何 `UPDATE topics`，恒为 NULL | 主题既不能改名也不能归档 |
| 12 | **README 措辞与实现有落差** | `README.md:25` 写"最近 50 场历史记录查找"，实际是"接口固定拉 50 场 + 前端标题子串过滤" | 用户以为能查全部历史 |

## 3. 目标与非目标

**目标（每条都要能被脚本验证）**

- **G1 找得回**：打开软件 3 秒内能接着上次学；任意一场都能按时间、主题、关键词定位。
- **G2 删得放心**：删除先进回收站，30 天内一键恢复；彻底删除仍然先给"删什么 / 留什么"的预演。
- **G3 有脉络**：一个主题下的所有场次按时间连成线，能看出"这个主题是怎么一步步学过来的"。
- **G4 能打理**：批量归档 / 恢复 / 导出；看得见占用并能清理。
- **G5 够快**：1 万场规模下首屏 < 300ms，筛选与搜索都走索引。

**非目标（明确不做，避免范围膨胀）**

- 不做云同步 / 多设备（本地优先是产品底线，见 `项目总览.md` 第四节）。
- 不改 `turns` 只追加的原则：历史系统只做**标记与视图**，绝不改对话原件（`store.ts:83-87`）。
- 不做自动删除：到期清理只针对回收站里的东西，正常场次永远不动。
- 不做 AI 自动打标签 / 自动摘要历史（成本与隐私，留到 v0.12 单独评估）。

## 5. 交互规则

### 5.1 列表、分组、分页

- 默认按**最近活动**倒序（`last_active_at`，没有就退回 `started_at`），同一天折叠成一组，组头是"今天 / 昨天 / 本周 / 更早"。
- 每页 50 条，滚到底自动加载下一页（游标 = 上一页最后一条的 `(last_active_at, id)`，不用 OFFSET，避免翻到后面越来越慢）。
- 置顶的场次永远在最上方（不分天、不排序），最多 5 个。

### 5.2 筛选与排序

| 维度 | 取值 | 备注 |
|---|---|---|
| 时间 | 全部 / 今天 / 本周 / 本月 / 自定义区间 | 按 `last_active_at` |
| 主题 | 全部 / 具体主题 / 无主题 | 取自 `topics` |
| 类型 | 全部 / 学习 / 资料整理 | 新字段 `kind`，见 §6 |
| 状态 | 全部 / 在读 / 已收线 / 已归档 / 回收站 | 在读 = `ended_at IS NULL` 且未归档 |
| 其他 | 只看有未收线 / 只看含资料 / 只看置顶 | 开关 |
| 排序 | 最近学习 / 最早 / 轮次最多 / 笔记最多 | 前两个用索引，后两个只在当前页内排 |

### 5.3 搜索（历史页内）

- 搜的范围：**标题 + 本场小结 + 主题名 + 对话正文 + 笔记 + 资料名**。
- 正文与笔记走已有的 FTS5（`search_fts`，`db.ts:179-214`），命中后按 `session_id` 聚合，列表里显示"命中的那一句 + 第几轮"，点进去直接跳到那一轮。
- 长度规则沿用现成口径：≥3 字走 FTS，<3 字走标题/小结的 `LIKE`（`search.ts:20-26`）。
- **与 ⌘K 的分工**：⌘K 是"找东西"（跨类型、跳到具体内容）；历史页搜索是"找那一场"（结果按场次聚合）。
- **前置改造**：`GET /sessions` 目前返回原始行、不带主题名，也没有 `/topics`。按主题筛选、分组、脉络都依赖这一步，必须先扩接口（在 §7 的参数基础上，返回体加 `topicTitle`）。

### 5.4 批量操作

多选后可以：归档 / 取消归档 / 导出（合并成一个 Markdown 或一个 ZIP）/ 删除（进回收站）。
不做批量"彻底删除"——那一步必须逐场看预演。

### 5.5 主题脉络

在主题名上点进去 → 该主题下的场次按时间排成一条线：

```
AI 入门 · 12 场 · 从 8/12 学到 9/30
● 8/12 第 1 场  什么是梯度下降          8 轮 · 3 条笔记
│   小结：…           未收线：学习率怎么选？
● 9/02 第 2 场  softmax 与数值稳定      12 轮 · 6 条笔记
…
```
每场可以"从这里继续"。这是把 G3 落地的地方，也是这个产品区别于普通聊天记录的地方。

### 5.6 恢复与彻底删除

- **删除 = 软删除**：进回收站，立刻从列表 / 搜索 / 地图 / 复习 / 未收线 / 本周回顾 / 统计里消失；数据库行一条不删。
- **恢复**：清空 `deleted_at`，主题归属、笔记、资料、位置全部照旧。
- **彻底删除**：仍然先弹现在的预演弹窗（`Chat.tsx:953-988`），确认后走 `store.deleteSession()`（含原件清理）。
- **保留期**：默认 30 天，设置里可选 7 / 30 / 90 / 永久；启动时清理过期项，清理失败只写日志、不阻塞启动。
- **清空回收站**：逐场走彻底删除，中途失败就停下并报告"已完成 N 场"。

> **删除的完整设计单独成篇：`docs\v0.11.0-删除设计.md`**（6 种删除粒度、两级删除与文案、批量与撤销、15 条边界情况、16 条专项验收）。
> 两处冲突时以那份为准。

## 6. 数据模型（数据库 v9）

> **实现状态**：v9 已随"删除系统"那一轮落地，但只包含删除需要的部分——`sessions.deleted_at`、
> `nodes.trashed_at`、两个索引，以及 `search_fts` 的删除触发器与孤儿行清理（见 `db.ts` 的 `SCHEMA_V9_*`）。
> 下面列出的 `pinned_at` / `kind` / `last_active_at` 属于历史页那一轮，**尚未实现**，落地时另起一个版本号。
> 删除相关的详细实现见 `v0.11.0-删除设计.md` 文末的「实现记录」。

沿用 `db.ts` 现有的迁移写法（`BEGIN` → 按版本号依次执行 → `user_version` → `COMMIT`，见 `db.ts:293-334`）。v8 → v9 **只加列与索引，不动任何已有数据**。

```sql
-- 1) 回收站：非空表示"已删除"，所有读取场次的地方都要排除它（见 §8）
ALTER TABLE sessions ADD COLUMN deleted_at TEXT;

-- 2) 置顶：非空表示置顶，界面永远排最前
ALTER TABLE sessions ADD COLUMN pinned_at TEXT;

-- 3) 类型：'chat' 普通学习 / 'document' 资料整理（由资料库导入时创建，见 server.ts:663-667）
ALTER TABLE sessions ADD COLUMN kind TEXT NOT NULL DEFAULT 'chat';

-- 4) 最近活动时间：聊天或整理时刷新；列表按它排序，比 started_at 更贴近"我上次学到哪"
ALTER TABLE sessions ADD COLUMN last_active_at TEXT;

-- 5) 列表与筛选的主索引（覆盖"未删除 + 未归档 + 倒序"这个最常见的查询）
CREATE INDEX idx_sessions_alive ON sessions(deleted_at, archived_at, last_active_at DESC);
CREATE INDEX idx_sessions_topic_alive ON sessions(topic_id, deleted_at, last_active_at DESC);

-- 6) 现有归档索引保留；v7 建的 idx_sessions_archived 不动
```

**同一个 v9 里顺手补两件数据卫生的事**（本轮盘点发现的既有问题，见 §14）：
```sql
-- 7) search_fts 目前只有 INSERT 触发器，没有 DELETE。
--    deleteSession() 级联删掉的 turns、重算删掉的 nodes 会在全文索引里留下永久孤儿行
--    （现在不会显示坏结果，因为 search.ts 查不到就跳过，但索引只增不减）。
CREATE TRIGGER IF NOT EXISTS search_turn_delete AFTER DELETE ON turns BEGIN
  DELETE FROM search_fts WHERE ref_kind = 'turn' AND ref_id = OLD.id;
END;
CREATE TRIGGER IF NOT EXISTS search_node_delete AFTER DELETE ON nodes BEGIN
  DELETE FROM search_fts WHERE ref_kind = 'node' AND ref_id = OLD.id;
END;
-- 8) 清掉历史遗留的孤儿行（一次性，可重复执行）
DELETE FROM search_fts WHERE ref_kind = 'turn' AND ref_id NOT IN (SELECT id FROM turns);
DELETE FROM search_fts WHERE ref_kind = 'node' AND ref_id NOT IN (SELECT id FROM nodes);
```

**`topics.archived_at` 怎么处理**：要么在 v0.11.0 把它用起来（主题归档），要么在 v0.11.1 顺手删掉这个恒为 NULL 的死列。**别让它继续躺着**——下一个人会以为主题归档已经实现了。

**为什么不在 `sessions` 上冗余轮次数 / 笔记数**：一页 50 行的相关子查询（走 `idx_turns_session`、`idx_note_blocks_node`）实测是毫秒级；用触发器维护冗余列，一旦漏掉某条写入路径就会出现"显示 8 轮实际 9 轮"的脏数据。宁可慢 5ms，不要数据漂移。**验收里加一条 EXPLAIN 检查守住这个决定**（见 §10）。

**统一判定收敛到一处**：像 v0.9.2 把"哪些节点属于本场"收敛成 `SESSION_NODE_SQL`（`store.ts:66-81`）一样，这次把"哪些场次算活着"收敛成 `Store` 里的一个常量/视图，禁止各处手写 `deleted_at IS NULL`。这是这版最容易出错的地方——漏一处，用户就会发现"删掉的场次还在复习里"。

## 8. 影响面清单（软删除必须一起改的地方）

**下面这些地方现在都在读 `sessions`，软删除上线时必须逐条确认已经排除已删除的场次。** 漏一处就是一个"删了还看得见"的 bug。

| # | 位置 | 功能 | 不改会怎样 |
|---|---|---|---|
| 1 | `store.ts:136` `latestSession()` | 启动时恢复上次那一场 | 启动后直接打开了回收站里的场次 |
| 2 | `store.ts:147` `listSessions()` | 历史列表 | 回收站里的场次还在列表里 |
| 3 | `store.ts:153` `listArchivedSessions()` | 归档列表 | 同上 |
| 4 | `store.ts:172` `map()` | 地图的主题默认场次 | 地图给节点指到一个已删场次 |
| 5 | `store.ts:421` `stats()` | 首页 / 设置里的统计 | 统计数字含已删除 |
| 6 | `server.ts:81-84` 闲置自动归航 | 20 分钟没动就自动收线 | **最危险**：回收站里的场次还会被自动归航调用模型，白花钱 |

## 9. 性能预算

| 场景 | 目标 | 手段 |
|---|---|---|
| 1 万场首屏 | < 300ms | `idx_sessions_alive` 覆盖排序；一页只取 50 行 |
| 每行统计（轮次/笔记/资料） | 50 行 < 20ms | 相关子查询走 `idx_turns_session` / `idx_note_blocks_node` / `idx_attachments_session`；**不允许全表扫描** |
| 历史页搜索 | < 150ms | 走 `search_fts`，按 `session_id` 聚合，最多取 200 条命中再分组 |
| 回收站占用 | < 50ms | `SUM(bytes) JOIN attachments`，只统计已删除场次 |
| 筛选下拉（facets） | < 20ms | 与列表同一个查询里算，或单独一条走索引的聚合 |

验收方式：`scripts/history-regression.cjs` 里对 5 条关键 SQL 跑 `EXPLAIN QUERY PLAN`，断言出现 `USING INDEX` 而不是 `SCAN sessions`。

## 12. 需要拍板的 5 个问题

1. **回收站保留期默认多久？** 建议 30 天（可选择 7/30/90/永久）。永久保留会更安心，但数据库只增不减。
2. **归档的场次还参与哪些计算？** 建议：不参与复习与"未收线"主页面，但仍计入本周回顾与学习统计（归档是"收起来"，不是"没发生过"）。
3. **资料整理场次算不算"一场学习"？** 建议：算一场，但打上 `kind='document'`，默认不计入学习统计与连续天数，历史页可单独筛。
4. **主题能不能改名 / 合并？** 影响面大（地图、笔记、导出都用主题）。建议 v0.11.1 单独评估，不要塞进这一版。
5. **回收站里的场次还允许导出吗？** 建议：允许（既然能恢复，就说明数据还在），但导出处明确标注"来自回收站"。

## 13. 风险与取舍

| 风险 | 说明 | 对策 |
|---|---|---|
| 软删除漏改读取点 | §8 的 16 处，漏一处就出现"删了还看得见" | 收敛成一个判定 + 16 条逐入口断言 |
